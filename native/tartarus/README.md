# Tartarus calculation core

Independent port authored from this repository's `js/engine.js` and the candidate ordering in `js/solver.js`. No external simulator implementation was used. `data.json` contains snapshots exported from our engine, solver and measured tool-combos modules.

Engine entry points:

- `engine::apply(state, action) -> bool`: solver action semantics. `stopchain` commits Cancel and EndDay.
- `engine::stop_chain(state) -> bool`: direct engine Cancel only, including action-event spawn.
- `engine::candidates(state) -> Vec<Value>`: action values in the JS order; JS owns human labels.
- Query helpers follow engine export names in snake_case. The JSON boundary preserves adapter metadata and optional observed restrictions; the internal state uses indexed typed records.

Inputs must be valid engine states with all required arrays/objects. Initial states come from the JS engine; native `newGame`, scene-editor/lab actions and save migration are not implemented. The native protocol must validate incoming shape before calling these functions. No logging, filesystem, capture, network, or game input exists inside the engine.

Both current engine and solver RNG implementations use wrapping uint32 mulberry32. Keep their independent stream states separate. engine::random implements the shared primitive; engine::rand updates a state object.

Presentation-only differences: `log` is preserved but not appended; `chaining.at` therefore tracks the existing log length, and bite `notes` are empty. Gameplay bite fields, board, hidden occupants, IDs, RNG, stats, restrictions, pending choices and result are retained. Parity normalization may omit only these presentation fields.

The worker selects this optional backend only when the runtime source and asset
seals match. The JS reference remains available for incompatibility and runtime
failures. The application keeps the existing launcher and Electron interface.

The policy/job implementation includes the original trained profiles and defaults,
chain value recursion and memoization, exact move scoring, measured tool subsets,
weighted reroll expectations, gift sampling, unseen future masking, playout,
common-random-number Monte Carlo rows and optional early-vault tracking.
`policy::chain_odds` exposes the independent explanatory probability recursion.
No ranking, tie preference, labels or narrative reason rendering is reimplemented:
the existing JS owns those functions and consumes the original-order raw rows.
Invalid candidate samples are represented by JSON null (JS transport restores NaN).
The internal model uses indexed records with exact field-presence tracking and
an unknown-field sidecar. A Job converts input once, then runs the same engine
and policy without JSON conversion between moves. Scalar field access, typed
strategy weights, board views and bounded pure caches avoid general JSON-map
work in the hot loop. The JSON API wrappers and trajectory diagnostic use the
same internal implementation.

The portable gate verifies complete policies, normalized gameplay state, raw
samples, early horizons and incremental transport against the current JS. The
constant snapshot is generated by `tools/snapshot-acceleration-data.js`.
Follow `ENHANCEMENTS.md` for reference updates and the explicit source build.

The same protocol is available through a local diagnostic CLI:
`cargo build --release --features solver --bin tartarus-core-cli`. Requests are
JSON lines on stdin, responses JSON lines on stdout. `info` describes the
contract; `init`/`step`/`solve` calculate sample rows, `cancel` releases the job,
and `apply`/`candidates`/`decide`/`trajectory` support deterministic verification.
Seeds/streams are uint32; use valid current-engine states. Native creation of
games, editing and persisted-profile migration remain JS responsibilities.
